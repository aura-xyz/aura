# Aura 技能创作指南

本文件是「怎么写一个在 Aura 里真的会用起来的技能」。**不要照搬其它 agent 平台的写法**——加载时机、工具名、执行环境都不一样。

> 本目录下 `agents/`、`eval-viewer/`、`scripts/` 来自上游 Claude Code 版本，Aura 没有对应运行时（没有启子代理、没有 `claude` CLI、没有后台 eval）。**不要调用它们**，也不要向用户承诺「跑一组评测」。

## 一、技能是什么

一份 `SKILL.md`（YAML Frontmatter + 正文），放在特定目录里，Aura 启动后扫描到它：

- **L1 索引**：每轮对话把**所有启用技能**的 `name` + `description` 塞进系统提示，模型据此判断「这事该不该用某个技能」。
- **L2 正文**：模型调用 `load_skill` 后才把正文放进上下文。所以正文可以写长，没被加载的技能不占 token。

这个机制决定了技能的两条铁律：

1. **`description` 决定命中率**，它写的是「什么时候用」，不是「这是什么」。写成产品说明书，模型就找不到触发点。
2. **正文只写模型不知道的东西**。模型本来就会写 Python、会 `git`，不用教；要写的是你的**约定、坑、验收标准、文件在哪**。

## 二、放哪里

| 位置 | 适合 | 谁能看到 | 你能写吗 |
|---|---|---|---|
| `<工作区>/.agents/skills/<name>/SKILL.md` | 项目特有的规范、脚本，随 Git 共享给团队 | 该工作区 | **能**（`write_file` 只能写工作区内） |
| 应用数据目录的 `skills/local/<name>/SKILL.md` | 个人常用、跨项目 | 本机所有工作区 | 不能，需要用户自己放 |
| 应用数据目录的 `skills/market/<name>/` | 从技能市场安装（别手改） | 本机 | 不能 |
| 安装目录 `builtin-skills/` | 随应用发布（开发者用） | 所有人 | 不能 |

同名技能按 **工作区 > 本地 > 市场 > 内置** 覆盖。

**重要**：工具只能写工作区。想做一个跨项目的个人技能，就在工作区的
`.agents/skills/` 里写好，再告诉用户把这个目录挪到应用数据目录的 `skills/local/`
（Skills 页上能看到真实路径）。不要试图直接写应用数据目录，那会被沙箱拒绝。

写完告诉用户：回到 `Skills` 页、重新进入一次就能看到（扫描是每轮重做的，页面在进入时读一次）。

## 三、Frontmatter 三个字段

```yaml
---
name: weekly-report          # 必填。小写字母/数字/._-，≤64 字符，全局唯一
description: 生成周报时使用。触发：用户说「写周报」「这周做了什么」「整理本周进展」，或明确要求按固定格式汇总本周工作。  # 必填，一句话说清「何时用」
version: 1.0.0               # 可选，缺省 0.0.0（市场据此判断能否更新）
allowed-tools:               # 强烈建议填
  - read_file
  - write_file
  - run_script
---
```

**`description` 写法**：先写用途（一句话），再列触发词（用户可能怎么开口），最后可选写「不要用于 X」。中文即可——用户用中文说话，用中文触发词命中率最高。

- 好：`把长文档拆成可执行的实施步骤时使用。触发：「拆一下这个方案」「落地步骤」「排期」。不要用于纯问答。`
- 坏：`一个强大的文档处理助手，支持多种格式，帮助用户高效完成工作。`（全是形容词，模型无法判断何时用）

**`allowed-tools` 语义**：技能激活期间，工具调用必须**同时**满足当前模式权限与这份白名单（求交集）。所以：

- 只会读的技能就别写 `write_file`——写了也不会更安全，只会让权限看起来更宽。
- 漏写必需工具 = 模型在技能激活期间用不了它，会莫名其妙地卡住。**列出这个技能真正需要的全部工具。**
- 留空 = 不收窄（继承当前模式权限）。仅当技能确实什么都可能用、且你接受这个范围时才留空。

可用工具名：`list_files`、`read_file`、`search_workspace`、`write_file`、`string_replace`、`replace_lines`、`run_script`、`load_skill`。写错名字会导致工具在激活期被全部拦掉——写完用 Skills 页看一眼「工具」那一行是不是你想要的。

## 四、正文怎么写

推荐骨架（按需增删）：

```markdown
# 一句话说明这个技能产出什么

## 何时用 / 何时不用        ← 边界，比步骤更重要
## 输入与前置检查          ← 缺什么就直接问，不要猜
## 步骤                    ← 编号，每步一个动作 + 验收点
## 验收                    ← 怎么判断做完了（可执行、可观察）
## 常见坑                  ← 具体到命令与报错
```

写作要点：

- **先给判断，再给步骤**。「按文档长度选方案：<20 页直接读；否则先切分」比「以下是十种方法」有用。
- **每条命令都要能直接执行**：写清楚工作目录、完整参数、引号。别写「用 python 处理一下」。
- **默认环境是 Windows + `cmd`**：没有 bash、没有 `unzip`/`grep`/`find`。跨平台就用 Python。
- **不要假设依赖已安装**：告诉模型先探测（`python -c "import x;print(1)"`），缺了就让用户装。
- **正文控制在 200～500 行**。细节放附属文件，让模型按需取（见下）。

## 五、附属文件与脚本

技能目录里可以放 `reference/`、`scripts/`、模板等。**模型读不到工作区之外的文件**，所以：

- 正文要引用附属文件时，明确写「用 `load_skill` 的 `file` 参数读取」，给出相对路径：
  `{"name": "weekly-report", "file": "reference/template.md"}`
- 自带脚本必须用**绝对路径**调用（相对路径会落在用户工作区里）：
  `python "C:/<skill_dir>/scripts/build.py" out.md`，`<skill_dir>` 由 `load_skill` 回执给出。
- 脚本只用手边有的运行时。想用第三方库就在正文里写清探测与安装命令。

## 六、写完怎么验

1. 在 `Skills` 页确认：技能出现、来源正确、工具行符合预期（不是空、也不是全量）。
2. 开一个**新会话**，用一句「用户会怎么说」的话去触发它（不要用技能名）。看模型有没有先 `load_skill` 再照做。
3. 没触发 → 改 `description` 的触发词，别改正文。
4. 触发了但做错 → 补「验收」与「常见坑」，把这次的具体错误写进去。
5. 收尾问一句「还有哪里不顺手」，根据反馈再迭代一轮。

一次只改一个变量（要么描述、要么正文），否则无法判断是哪里起的作用。
